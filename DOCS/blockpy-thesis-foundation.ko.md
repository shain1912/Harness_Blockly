# BlockPy 완전 해설: 블록과 파이썬을 무손실로 잇는 컴파일러

## 이 문서는 무엇인가 · 누구를 위한 것인가 · 논문에 어떻게 쓰나

**이 문서는 무엇인가.** BlockPy는 "블록(그림 조각)"과 "파이썬(글자 코드)"을 **양쪽으로, 뜻을 하나도 잃지 않고** 오가게 만드는 도구다. 이 문서는 그 도구가 무엇을 위해 만들어졌고, 어떤 원리로 동작하며, 코드 수준에서 어떻게 구현되었고, 학술적으로 어떤 기여를 주장할 수 있는지를 **하나의 흐름으로** 설명한다. 크게 네 부분으로 이뤄진다.

1. **컴파일러 용어와 개념**(1장) — 소스코드·토큰·파서·AST·IR처럼, 나머지 이야기를 읽는 데 꼭 필요한 낱말을 비유와 함께 익힌다.
2. **블록코딩 용어와 개념**(2장) — 블록·워크스페이스·툴박스·shadow 블록 같은 시각 프로그래밍의 기본을 익히고, BlockPy가 이를 어떻게 특별하게 쓰는지 본다.
3. **BlockPy 구현 상세**(3장) — 실제 코드(함수 이름·파일 경로)를 따라가며 파이썬↔블록 변환이 어떻게 무손실로 이뤄지는지 들여다본다.
4. **연구/논문 프레이밍**(4장) — 이 모든 것을 학술 기여·관련 연구 비교·평가 방법론·논문 초록으로 정식화한다.

**누구를 위한 것인가.** 앞에서부터 순서대로 읽으면 **처음 코딩을 배우는 고등학생**도 이해할 수 있도록 "용어 → 개념 → 블록코딩 → 구현 → 논문"의 난이도 순으로 배치했다. 1·2장은 배경지식이 없어도 읽을 수 있고, 3장은 개발자·연구 보조자를 위한 기술 상세이며, 4장은 논문을 쓰려는 사람을 위한 것이다. 어려운 뒷장이 막히면 앞장의 용어와 맨 뒤의 **미니 사전**으로 돌아오면 된다.

**논문에 어떻게 쓰나.** 1·2장은 논문의 배경(Background)·용어 정리 절의 재료다. 3장은 시스템 구현(System / Implementation) 절과 재현성(Reproducibility) 근거로 쓸 수 있으며, 실제 함수·파일·테스트 자산을 그대로 인용할 수 있다. 4장은 그 자체로 논문의 골격(문제 정의·기여·관련 연구·평가·초록)이다. 특히 4장이 제시하는 두 축 — **"진짜 언어의 AST를 단일 IR로 삼아 무손실을 증명 가능하게 한다"**와 **"recognition(인식) ⟂ lowering(생성)을 분리해 오라클 오류가 코드를 오염시키지 못하게 한다"** — 이 논문의 핵심 주장이며, 1~3장 전체가 이 두 문장을 뒷받침하도록 짜여 있다.

---

## 목차

- **1. 컴파일러 용어와 개념** — 소스코드, 토큰/렉서, 파서, 문법, AST, 노드, IR, 코드 생성/unparse, lowering, 컴파일 vs 인터프리트, 왕복, 무손실, AST 동일성, 전수성(raw=0), fail-loud
- **2. 블록코딩 용어와 개념** — 시각 프로그래밍, Blockly, 블록, 워크스페이스, 툴박스/카테고리, 플라이아웃, 연결(문장 블록 vs 값 블록), shadow 블록, 필드, 뮤테이터, 직렬화, 제너레이터, 교육적 이점, BlockPy의 세 가지 설계
- **3. BlockPy 구현 상세** — **한 프로그램의 여행 `x = 3 + 4`(실제 IR·블록 JSON 미리보기)**, 단일 IR, 무손실 계약·증명, 상수 태깅·주석 보존, 파이썬→블록/블록→파이썬(거울상 핸들러 코드), recognition⟂lowering, 임의 라이브러리 introspection, 큐레이션, 오프라인 패키징, 검증 — **각 절에 실제 코드 예시 + 비유**
- **4. 연구/논문 프레이밍** — 문제 정의, 네 갈래 기여, 관련 연구 비교, 평가 방법론, 논문 제목·초록 초안
- **부록. 핵심 용어 미니 사전(가나다)**

이 문서 전체에서 표기를 다음과 같이 통일한다. 되돌아온 결과가 원본과 뜻이 같음 = **무손실(lossless)**, 한 바퀴 여행 = **왕복(round-trip)**, 파싱 후 트리가 같음 = **AST 동일성**, 모든 노드를 빠짐없이 처리함 = **전수성(raw=0)**, 틀리면 조용히 넘기지 않고 멈춤 = **fail-loud**, 블록의 "색칠/알아채기"와 "코드로 내려쓰기"의 분리 = **recognition ⟂ lowering**. 이 여섯 낱말이 문서 전체를 관통하는 뼈대다.

# 1. 컴파일러 용어와 개념

프로그램을 만든다는 것은 결국 "사람이 이해하는 말"을 "컴퓨터가 이해하는 말"로 바꾸는 일이다. 이 번역을 담당하는 장치가 바로 **컴파일러(compiler)**다. BlockPy는 조금 특별한 컴파일러인데, 사람이 이해하는 말(파이썬 글자)과 사람이 눈으로 보는 그림(블록)을 **양쪽으로** 오가게 만든다. 이 장에서는 그 여행에 필요한 낱말들을 하나씩 익혀 보자. 여기서 배운 용어는 2장의 블록코딩, 3장의 구현, 4장의 논문 전체에서 그대로 쓰인다.

---

## 소스코드 (source code)

**쉬운 정의**: 사람이 직접 키보드로 쳐서 쓴, 프로그램의 원본 글자.

**비유**: 요리사가 손으로 쓴 "레시피 원본"이다. 아직 요리가 된 것은 아니고, 무엇을 어떻게 하라고 적어 둔 종이다.

**BlockPy 예시**: 파이썬 편집기 칸에 학생이 직접 타이핑한 이런 글자가 소스코드다.

```python
x = 3 + 4
print(x)
```

BlockPy에서 소스코드는 두 얼굴을 가진다. 하나는 이런 파이썬 텍스트, 다른 하나는 화면 위의 블록 그림이다. BlockPy의 목표는 이 둘을 완벽히 같은 뜻으로 유지하는 것이다.

---

## 토큰 / 렉서 (token / lexer·tokenizer, 토큰 나누기)

**쉬운 정의**: **토큰**은 소스코드를 잘게 쪼갠 "의미 있는 최소 조각"이다. **렉서(lexer)**는 글자들을 이 토큰 조각들로 잘라 주는 도구다.

**비유**: 우리가 "나는밥을먹었다"라는 붙어 있는 글자를 읽을 때, 머릿속에서 자동으로 "나 / 는 / 밥 / 을 / 먹었다"로 끊어서 이해한다. 렉서가 하는 일이 바로 이 "띄어 읽기"다. 잘려 나온 낱말 하나하나가 토큰이다.

**BlockPy 예시**: `x = 3 + 4`라는 한 줄은 렉서를 거치면 이렇게 여섯 개의 토큰이 된다.

| 토큰 | 종류 |
|---|---|
| `x` | 이름(변수) |
| `=` | 대입 기호 |
| `3` | 숫자 |
| `+` | 더하기 기호 |
| `4` | 숫자 |

BlockPy는 파이썬을 직접 손으로 자르지 않고, 진짜 파이썬(Pyodide 안의 CPython)에게 이 일을 맡긴다. 파이썬의 표준 도구인 `tokenize`가 렉서 역할을 하며, 특히 **주석(#으로 시작하는 설명 글)**을 정확히 뽑아내는 데 쓰인다.

---

## 파서 (parser, 구문 분석기)

**쉬운 정의**: 잘려 나온 토큰들을 보고 "이 문장의 구조가 무엇인지" 알아내는 도구.

**비유**: 렉서가 "나 / 는 / 밥 / 을 / 먹었다"로 낱말을 끊었다면, 파서는 "아, 이건 **누가(나) + 무엇을(밥) + 어쨌다(먹었다)** 형태의 문장이구나" 하고 문장의 뼈대를 알아내는 국어 선생님이다.

**BlockPy 예시**: 파서는 `x = 3 + 4`의 토큰들을 보고 "이것은 **대입문**이다. 왼쪽은 변수 `x`, 오른쪽은 `3 + 4`라는 **덧셈식**이다"라는 구조를 파악한다. BlockPy에서는 `ast.parse`라는 진짜 파이썬 파서가 이 일을 한다.

---

## 문법 (grammar, 문장을 만드는 규칙)

**쉬운 정의**: 어떤 토큰 배열이 "말이 되는 문장"이고 어떤 것이 "말이 안 되는 문장"인지를 정해 둔 규칙 모음.

**비유**: 한국어에서 "나는 밥을 먹었다"는 맞지만 "밥을 나는 먹었다를"은 어색하다. 이렇게 "올바른 문장의 모양"을 정한 것이 문법이다. 파서는 이 문법책을 기준으로 문장을 판단한다.

**BlockPy 예시**: 파이썬 문법은 `x = 3 + 4`는 허용하지만 `x = = 4`는 틀렸다고 본다. BlockPy는 파이썬의 진짜 문법을 그대로 따르므로, 파이썬에서 되는 것은 되고 안 되는 것은 안 된다. 별도의 "BlockPy만의 문법"을 새로 만들지 않는다는 점이 중요하다.

---

## AST (Abstract Syntax Tree, 추상 구문 트리)

**쉬운 정의**: 파서가 알아낸 문장의 구조를 **나뭇가지 모양(트리)**으로 그린 그림. 괄호나 띄어쓰기 같은 겉모습은 버리고("추상") 뜻만 남긴다.

**비유**: 가족 관계도(족보)와 같다. 맨 위에 할아버지가 있고, 그 아래 자식, 또 그 아래 손자가 가지처럼 뻗어 나간다. "추상"이라는 말은, 예를 들어 `3 + 4`와 `3+4`처럼 띄어쓰기만 다른 것은 **똑같은 트리**가 된다는 뜻이다. 겉모습은 무시하고 속뜻만 그린다.

**BlockPy 예시**: `x = 3 + 4`의 AST는 이렇게 생겼다.

```
대입(Assign)
├── 대상: 변수 x
└── 값: 덧셈(BinOp: +)
        ├── 왼쪽: 숫자 3
        └── 오른쪽: 숫자 4
```

BlockPy의 심장이 바로 이 AST다. BlockPy는 CPython 3.12의 `ast`(파이썬이 실제로 쓰는 그 트리)를 그대로 자기 것으로 삼는다. 새로운 트리를 발명하지 않고, 진짜 언어가 쓰는 트리를 빌려 쓴다.

---

## 노드 (node, 나무의 마디)

**쉬운 정의**: 트리를 이루는 **점 하나하나**. 각 노드는 "이것은 대입이다", "이것은 숫자 3이다"처럼 한 가지 역할을 맡는다.

**비유**: 족보에서 사람 한 명 한 명이 노드다. 지하철 노선도의 역 하나하나라고 봐도 좋다.

**BlockPy 예시**: 위 트리에서 `대입`, `변수 x`, `덧셈`, `숫자 3`, `숫자 4`가 각각 노드다. 파이썬 AST에는 대입(`Assign`), 함수 호출(`Call`), 반복(`For`), 조건(`If`) 등 여러 종류의 노드가 있다. BlockPy는 이 노드 하나하나를 화면의 블록 하나하나로 대응시킨다. 즉 **파이썬 노드 = BlockPy 블록**이라는 짝짓기가 핵심이다.

---

## IR (Intermediate Representation, 중간표현)

**쉬운 정의**: 사람의 언어(파이썬 글자)와 화면의 그림(블록) 사이에 놓인 **중간 다리 표현**. 양쪽 어느 쪽으로도 쉽게 바뀔 수 있는 "가운데 형태".

**비유**: 한국어를 아랍어로, 아랍어를 한국어로 오가야 하는 통역소가 있다고 하자. 두 언어를 직접 이으면 너무 복잡하니, 가운데에 **영어**를 두고 "한국어↔영어↔아랍어"로 오간다. 이 가운데 영어가 IR이다. 모두가 거쳐 가는 공통 중간 지점이다.

**BlockPy 예시**: BlockPy의 IR은 **파이썬 AST를 JSON(글자로 표현한 데이터)으로 적어 둔 것**이다. 흐름은 이렇다.

```
파이썬 글자  ──pythonToIR──▶  IR(=AST를 담은 JSON)  ──irToBlockly──▶  블록 그림
블록 그림    ──blocklyToIr──▶  IR(=AST를 담은 JSON)  ──irToPython──▶  파이썬 글자
```

여기서 `pythonToIR`은 파이썬을 파싱해 AST를 JSON으로 직렬화(글자로 저장)하고, `irToPython`은 그 JSON을 다시 AST로 되살려 파이썬 글자로 되돌린다. **IR 하나만 튼튼하면, 파이썬 쪽과 블록 쪽을 따로따로 이 IR에만 연결하면 되므로** 전체가 단순해진다.

---

## 코드 생성 / unparse (codegen / unparse, 다시 글자로 되돌리기)

**쉬운 정의**: 트리(AST)나 IR을 보고 **사람이 읽을 수 있는 글자 코드로 다시 써 내려가는 것**. 파서의 정반대 방향이다.

**비유**: 파서가 "문장 → 뼈대 분석"이라면, unparse는 "뼈대 → 다시 완성된 문장". 족보 그림을 보고 "이 사람은 누구의 자식이고…"라며 줄글로 풀어 설명하는 것과 같다.

**BlockPy 예시**: 학생이 블록을 조립하면 BlockPy는 그 블록을 IR로 바꾼 뒤, 파이썬의 `ast.unparse`로 IR을 다시 파이썬 글자로 써 준다. 그래서 블록을 옮길 때마다 옆 칸의 파이썬 코드가 자동으로 새로 쓰인다. BlockPy는 여기에 더해 아까 뽑아 두었던 주석까지 제자리에 다시 끼워 넣는 특별한 unparser(`_CommentUnparser`)를 쓴다.

---

## lowering (낮추기)

**쉬운 정의**: "높은 수준의 편한 표현"을 "낮은 수준의 기본 표현"으로 풀어 내리는 것. 겉으로 화려해 보이는 것을 컴퓨터가 다루기 쉬운 밑바탕 형태로 바꾼다.

**비유**: "라면 끓여"라는 한 마디(높은 수준)를, "물 500mL를 냄비에 넣어라 / 끓여라 / 면을 넣어라 / 스프를 넣어라"라는 구체적 단계들(낮은 수준)로 풀어 쓰는 것이다. 뜻은 같지만 더 잘게, 더 기본적인 명령으로 내린다.

**BlockPy 예시**: BlockPy에서 lowering은 **블록 → IR(AST 노드)** 방향에서 일어난다(`blocklyToIr`). 예를 들어 특정 라이브러리용으로 예쁘게 꾸며진 "스킨(skin) 블록"도, 낮출 때는 일반적인 함수 호출(`Call`) 노드로 똑같이 내려온다. 즉 겉모습(색·라벨)이 달라도 밑바탕 IR은 하나로 모인다. **이 lowering 결과가 BlockPy가 만드는 파이썬 코드의 유일한 진짜 근거(source of truth)다.** 블록이 무슨 색이든, 어떤 라벨이 붙었든, 최종 파이썬은 오직 이 lowering된 구조에서만 나온다. (이 원칙은 2장의 "인식 ⟂ 번역 분리"와 4장의 "건전성 정리"로 이어지는 핵심이다.)

## 컴파일 vs 인터프리트 (compile vs interpret)

**쉬운 정의**: **컴파일**은 코드를 미리 통째로 다른 형태로 번역해 두는 것. **인터프리트(해석 실행)**는 코드를 한 줄씩 즉석에서 읽어 가며 바로 실행하는 것.

**비유**: 컴파일은 외국어 책 전체를 미리 번역해 번역본을 만들어 두는 번역가다. 인터프리트는 외국인 옆에 붙어 한 문장씩 그때그때 통역해 주는 통역사다.

**BlockPy 예시**: BlockPy는 두 가지를 다 쓴다.
- **컴파일 쪽**: 파이썬↔블록 변환은 코드를 미리 IR로 번역해 두는 컴파일에 가깝다.
- **인터프리트 쪽**: [Run] 버튼을 누르면 Pyodide(브라우저 안의 진짜 파이썬)가 코드를 실제로 한 줄씩 실행해 결과를 보여 준다.

---

## 왕복 (round-trip)

**쉬운 정의**: 어떤 것을 A→B로 바꿨다가 다시 B→A로 되돌려 오는 **한 바퀴 여행**.

**비유**: 한국어 문장을 영어로 번역했다가, 그 영어를 다시 한국어로 번역해 보는 것이다. 좋은 번역이라면 처음 문장과 뜻이 똑같이 돌아와야 한다.

**BlockPy 예시**: "파이썬 → 블록 → 다시 파이썬"이 한 번의 왕복이다. BlockPy의 존재 이유가 바로 이 왕복이 **깨지지 않게** 하는 것이다. 학생이 블록으로 바꿨다가 다시 글자로 돌아왔을 때, 원래 하려던 프로그램이 그대로 남아 있어야 한다.

---

## 무손실 (lossless, 잃는 것 없음)

**쉬운 정의**: 왕복을 해도 **아무 정보도 잃지 않는 것**. 되돌아온 결과가 원본과 뜻이 완전히 같다.

**비유**: 사진을 압축했다 풀었더니 흐려지면 "손실(lossy)"이고, 전혀 흐려지지 않으면 "무손실(lossless)"이다. 좋은 지퍼백처럼, 넣었다 뺐는데 안의 물건이 하나도 안 상한 상태다.

**BlockPy 예시**: BlockPy는 JSON으로 그냥 담으면 뭉개질 위험이 있는 까다로운 값들 — 바이트열(bytes), 복소수(complex), 무한대(inf)나 not-a-number(nan), 2의 53제곱을 넘는 아주 큰 정수, `1.0`처럼 정수처럼 보이는 실수 등 — 을 `{__py__: ...}`라는 특별한 꼬리표로 감싸서 원본 그대로 보존한다. 주석도 버리지 않고 노드에 붙여 되살린다. 그래서 왕복해도 잃는 게 없다. (구체적 구현은 3.3절에서 다룬다.)

---

## AST 동일성 (AST equivalence)

**쉬운 정의**: 두 코드가 **글자 그대로 같은지**가 아니라, **트리(AST)로 봤을 때 같은지**를 따지는 것. 무손실을 검사하는 진짜 기준이다.

**비유**: "안녕하세요"와 "안녕하세요."(마침표만 다름)를 글자로 비교하면 다르지만, "인사말이다"라는 **의미로 보면** 같다. AST 동일성은 이 "의미로 보면 같다"를 기계적으로 확인하는 방법이다. `3 + 4`와 `3+4`는 띄어쓰기만 다르지 트리는 똑같으므로 AST 동일이다.

**BlockPy 예시**: BlockPy가 지키는 계약은 이 한 줄로 요약된다.

```
ast.dump(parse(원본))  ==  ast.dump(parse(왕복 결과))
```

즉 원본 파이썬의 트리와, 블록을 거쳐 되돌아온 파이썬의 트리가 **완전히 같아야** 한다. 띄어쓰기나 줄바꿈이 조금 달라지는 것은 괜찮지만, **뜻이 바뀌면 실패**다. BlockPy는 이 검사를 186개의 테스트, 무작위로 만든 프로그램들(퍼즈, fuzz), 187개의 실제 코드 사례로 끊임없이 확인한다.

---

## 전수성 (totality / raw=0, 빠짐없이 모두 처리)

**쉬운 정의**: 파이썬에 있는 **모든 종류의 노드를 하나도 빠짐없이** 블록으로 처리할 수 있다는 성질. "raw=0"은 "처리 못 해서 날것(raw)으로 흘려보낸 노드가 0개"라는 뜻이다.

**비유**: 학교 급식에서 "우리 식당은 어떤 알레르기 재료가 와도 전부 대응표가 있다. 모르는 재료는 단 하나도 없다"라고 장담하는 것과 같다. 처리 못 하는 예외를 남겨 두지 않는다.

**BlockPy 예시**: `NODE_POLICY`라는 규칙표가 CPython 3.12의 **모든** ast 노드 종류를 분류해 둔다. 그리고 `ir_coverage.spec.js`라는 테스트가 "정말 빠진 노드가 하나도 없는가?"를 **기계가 자동으로** 검사한다. 사람이 "아마 다 됐겠지"라고 넘기지 않고, 컴퓨터가 전수 검사로 raw=0을 보증한다.

---

## fail-loud (틀리면 시끄럽게 멈추기)

**쉬운 정의**: 뭔가 모르거나 잘못됐을 때, **조용히 얼버무리지 않고 크게 소리치며 멈추는** 태도. 반대말은 "조용히 틀리기(silent failure)"다.

**비유**: 자동차에 문제가 생겼을 때, 아무 일 없는 척 계속 달리는 차(위험!)와, 경고등을 켜고 "여기 이상 있어요!"라고 즉시 알리는 차가 있다. fail-loud는 후자다. 잘못을 감추지 않으니 오히려 안전하다.

**BlockPy 예시**: BlockPy는 두 곳에서 이 원칙을 지킨다.
- **IR → 블록** 방향에서 모르는 노드를 만나면, 대충 넘기지 않고 `noHandler`로 **큰 소리로 멈춘다**. 조용히 틀린 블록을 만드느니 멈추는 편이 낫다는 것이다.
- **블록 → IR** 방향에서 `ir_*`가 아닌 엉뚱한 블록을 만나면 바로 오류를 던진다(throw).

이렇게 하면 "겉으로는 멀쩡해 보이는데 속으로 조용히 틀린" 최악의 상황을 막을 수 있다. 틀릴 바에는 눈에 띄게 틀려야 고칠 수 있기 때문이다.

---

### 1장 한눈에 정리

지금까지의 낱말들을 BlockPy의 여행 순서로 이으면 이렇게 된다.

```
파이썬 소스코드
   │  렉서(토큰 나누기) → 파서(문법으로 구조 분석)
   ▼
 AST (노드들로 이뤄진 트리)  ── 이것을 JSON으로 적으면 = IR ──
   │                                    │
   │ irToBlockly                        │ irToPython(unparse)
   ▼                                    ▼
 블록 그림  ──blocklyToIr(lowering)──▶  IR  ──▶ 다시 파이썬 소스코드
                                              (왕복 · 무손실 · AST 동일성으로 검증)
```

이 전체 여행이 **한 바퀴(왕복) 돌아도 뜻이 그대로(무손실)**이고, **모든 노드를 빠짐없이(전수성)** 다루며, **모르면 조용히 틀리지 않고 멈추는(fail-loud)** 것 — 이것이 BlockPy가 컴파일러 기술로 이루려는 약속이다. 그런데 이 그림의 오른쪽 끝, "블록 그림"이란 정확히 무엇일까? 다음 장에서 그 블록의 세계로 들어가 보자.

# 2. 블록코딩 용어와 개념

1장에서 파이썬 글자가 토큰·파서를 거쳐 AST가 되고, 그 AST가 IR을 통해 "블록 그림"으로 바뀐다는 큰 그림을 봤다. 이제 그 **블록 그림** 쪽을 자세히 들여다볼 차례다. 프로그래밍을 글자로 배우기 전에, 요즘은 많은 학생이 **블록(block)**을 조립하며 코딩에 입문한다. 스크래치(Scratch)를 한 번이라도 만져 봤다면 이미 절반은 아는 셈이다. 이 장에서는 블록코딩의 기본 용어를 하나씩 짚고, 그것이 BlockPy에서 구체적으로 어떻게 나타나는지 살펴본다. BlockPy는 이 블록들을 단순한 장난감이 아니라 **진짜 파이썬(Python) 코드와 1:1로 정확히 맞바꿀 수 있는 도구**로 쓴다는 점이 특별하다.

## 2.1 시각 프로그래밍(visual programming)이란

- **쉬운 정의**: 코드를 글자로 타이핑하는 대신, 그림처럼 생긴 조각(블록)을 마우스로 끌어다 맞춰서 프로그램을 만드는 방식이다. "블록 기반 프로그래밍(block-based programming)"이라고도 부른다.
- **일상 비유**: 레고(Lego)를 떠올리면 된다. 아무 부품이나 다 이어 붙일 수 있는 게 아니라, 튀어나온 돌기와 파인 홈이 맞는 것끼리만 딸깍 끼워진다. 그래서 "말이 안 되는 조립"이 애초에 잘 안 만들어진다.
- **BlockPy에서**: 왼쪽 서랍에서 블록을 끌어와 오른쪽 화면에 쌓으면, 그와 똑같은 뜻의 파이썬 코드가 실시간으로 만들어진다. 반대로 파이썬을 입력하면 그에 맞는 블록으로 되돌아온다. 즉 블록과 글자 코드가 **양방향(bidirectional)**으로 오간다. (이것이 1장에서 말한 "왕복"의 사용자 눈높이 모습이다.)

왜 글자 대신 블록일까? 초보자가 겪는 가장 큰 좌절은 대개 "무엇을 할지 몰라서"가 아니라 **문법 오류(콜론 빠짐, 괄호 안 닫음, 들여쓰기 실수)** 때문이다. 블록은 형태가 맞는 것끼리만 연결되므로, 이런 사소한 실수로 프로그램이 통째로 멈추는 일을 원천 봉쇄한다.

## 2.2 Blockly(블록클리) — 구글이 만든 블록 엔진

- **쉬운 정의**: Blockly는 구글(Google)이 만들어 무료로 공개한 **블록 프로그래밍 라이브러리(library, 미리 만들어 둔 기능 꾸러미)**다. 웹 페이지 안에서 블록을 끌고, 붙이고, 코드로 바꾸는 기능 전체를 제공한다.
- **일상 비유**: 스크래치가 "완성된 게임기"라면, Blockly는 "그 게임기를 만들 수 있는 부품 키트"에 가깝다. 개발자가 이 키트로 자기만의 블록 코딩 환경을 조립한다.
- **BlockPy에서**: BlockPy의 화면에 보이는 블록·서랍·연결 동작은 전부 Blockly가 담당한다. 다만 BlockPy는 Blockly가 기본 제공하는 블록을 그대로 쓰지 않고, **파이썬 문법 구조에 딱 대응하는 자기만의 블록(`ir_*` 블록, 2.14에서 설명)**을 새로 정의해 얹었다.

## 2.3 블록(block)

- **쉬운 정의**: 명령 하나, 값 하나를 나타내는 색색의 조각이다. "화면에 출력하라", "숫자 3", "만약 ~라면" 같은 하나의 뜻을 담는다.
- **일상 비유**: 문장을 이루는 단어 하나하나와 같다. 단어를 순서대로 늘어놓으면 문장이 되듯, 블록을 쌓으면 프로그램이 된다.
- **BlockPy에서**: `print(...)`에 해당하는 블록, 변수에 값을 넣는 블록, 반복문 블록처럼, 파이썬으로 쓸 수 있는 표현 하나하나가 각각의 블록으로 존재한다. 1장의 표현대로, **파이썬 AST 노드 하나 = 블록 하나**다.

## 2.4 워크스페이스(workspace) — 블록을 늘어놓는 캔버스

- **쉬운 정의**: 블록을 실제로 끌어다 놓고 조립하는 넓은 작업 공간(캔버스)이다.
- **일상 비유**: 그림을 그리는 도화지, 또는 레고를 늘어놓는 책상 판이다. 여기에 놓인 것만이 "내 작품"이다.
- **BlockPy에서**: 오른쪽 편집 영역이 워크스페이스다. 여기에 쌓인 블록들의 배치를 읽어서, 아래에 파이썬 코드가 생성된다. 워크스페이스에 없는 블록(아직 서랍 안에 있는 블록)은 프로그램에 포함되지 않는다.

## 2.5 툴박스(toolbox)와 카테고리(category)

- **쉬운 정의**: 쓸 수 있는 블록들이 종류별로 정리되어 있는 **메뉴 목록**이다. 종류별 묶음을 카테고리라고 한다.
- **일상 비유**: 공구함(toolbox)의 서랍이 "드라이버 칸", "망치 칸"으로 나뉜 것과 같다. 필요한 도구가 어느 칸에 있는지 알면 금방 꺼낸다.
- **BlockPy에서**: 툴박스는 왼쪽에 세로로 놓인 카테고리 목록이다. "제어(if·for)", "값·연산" 같은 파이썬 기본 문법 카테고리뿐 아니라, **불러온 라이브러리(예: `cv2`, `requests`)마다 별도 카테고리**가 생기고 색으로 구분된다. 어떤 파이썬 라이브러리든 블록으로 만들어 이 툴박스에 얹을 수 있다(3.7절 참조).

## 2.6 플라이아웃(flyout) — 서랍이 튀어나오는 순간

- **쉬운 정의**: 툴박스의 카테고리를 클릭했을 때 옆으로 **미리보기처럼 펼쳐지는 블록 목록** 창이다.
- **일상 비유**: 공구함의 한 서랍을 잡아당기면 안에 든 도구가 쭉 보이는 것과 같다. 도구를 하나 집어(끌어) 밖으로 꺼내면 서랍은 다시 닫힌다.
- **BlockPy에서**: 카테고리 이름을 누르면 그 안의 블록들이 플라이아웃으로 펼쳐진다. 원하는 블록을 워크스페이스로 끌어오면 플라이아웃은 닫힌다. 플라이아웃 안의 블록은 아직 "견본"이라, 끌어와 워크스페이스에 놓기 전까지는 코드에 반영되지 않는다.

## 2.7 블록 연결(connection): 문장 블록 vs 값 블록

블록끼리 붙는 자리를 **연결점(connection)**이라 하고, 연결 방식에 따라 블록의 성격이 갈린다. 이 구분이 블록코딩 이해의 핵심이다.

- **문장 블록(statement block, 쌓기 블록)**
  - *정의*: 위아래로 차곡차곡 **쌓이는** 블록. "이 동작을 하고, 그다음 저 동작을 하라"처럼 실행 순서를 이룬다.
  - *비유*: 레고를 위로 한 층씩 올리는 것. 또는 요리 레시피의 "1단계 → 2단계 → 3단계" 순서.
  - *BlockPy 예*: `x = 3` 대입 블록, `print(x)` 블록, `for` 반복 블록처럼 파이썬에서 한 줄(문장, statement)을 차지하는 것들.

- **값 블록(value block, 끼우기 블록) / 리포터(reporter)**
  - *정의*: 다른 블록의 **홈 안에 쏙 끼워져** 하나의 "값"을 대신하는 블록. 스스로 실행되기보다 값을 돌려준다(그래서 report한다는 뜻으로 리포터라 부른다).
  - *비유*: 문장 속 빈칸을 채우는 단어. "나는 ___을 좋아한다"의 빈칸에 "사과"를 끼우는 것과 같다.
  - *BlockPy 예*: 숫자 `3`, 문자열 `"안녕"`, `a + b` 덧셈 결과처럼 값을 만들어 내는 블록들. 이들은 `print( )` 블록의 괄호 홈이나 `x = ( )` 블록의 오른쪽 홈에 끼워진다.

> 요컨대 **문장 블록은 세로로 쌓이고, 값 블록은 가로로 끼워진다.** 파이썬으로 치면, 문장 블록은 한 줄의 명령(statement)이고 값 블록은 그 줄 안에 들어가는 식(expression)이다.

## 2.8 shadow 블록(그림자 블록) — 기본값 자리끼움

- **쉬운 정의**: 값이 들어갈 홈에 **미리 흐릿하게 채워져 있는 기본값 블록**이다. 사용자가 아직 아무것도 안 끼웠을 때 자리를 지켜 준다.
- **일상 비유**: 서류 양식의 빈칸에 회색 글씨로 적힌 "예시: 홍길동" 같은 안내 문구. 진짜 내용을 적으면 그 회색 글씨는 사라진다.
- **BlockPy에서**: 예를 들어 반복 횟수를 넣는 홈에 shadow로 숫자 `10`이 미리 들어가 있다. 그대로 쓰면 10번 반복하고, 다른 값 블록을 끌어다 끼우면 shadow는 밀려나 대체된다. 덕분에 학생이 아무것도 안 채워도 프로그램이 **말이 되는 상태**를 유지한다.

## 2.9 필드(field) — 블록 안에서 직접 채우는 칸

- **쉬운 정의**: 블록에 박혀 있어 직접 값을 입력하거나 고르는 작은 입력 칸이다. 종류로는 **텍스트 칸, 드롭다운(dropdown, 목록에서 고르기), 변수 선택 칸** 등이 있다.
- **일상 비유**: 설문지에서 이름을 적는 빈칸(텍스트), 성별을 고르는 선택 목록(드롭다운)에 해당한다.
- **BlockPy에서**: 여기에 BlockPy만의 중요한 원칙이 있다. 함수 이름·메서드 이름 같은 **구조적으로 정해진 이름은 수정 불가능한 고정 라벨**로 두고, 변수는 자유 입력이 아니라 **드롭다운으로만** 고르게 한다(2.14 참조). 자유 텍스트 칸은 리터럴 값이나 식별자처럼 확실한 것만 허용하고, 이상한 입력은 즉시 거부한다. 이 "이상하면 바로 거부"가 1장에서 배운 **fail-loud**의 사용자 눈높이 버전이다. 오타로 인한 엉뚱한 코드 생성을 막기 위해서다.

## 2.10 뮤테이터(mutator) — 블록의 모양을 바꾸는 장치

- **쉬운 정의**: 블록의 **구조 자체를 늘리거나 줄이는** 기능이다. 흔히 블록 위의 `[+]` / `[-]` 버튼으로 나타난다.
- **일상 비유**: 식탁을 손님 수에 맞춰 판을 덧대 늘렸다 줄였다 하는 확장형 테이블과 같다. 기본 골격은 그대로지만 자리 수가 바뀐다.
- **BlockPy에서**: 함수 호출 블록에 붙은 `[+]` `[-]` `[+kw]` 버튼이 대표적인 뮤테이터다. `[+]`를 누르면 인자(argument, 함수에 넘기는 값)를 끼울 홈이 하나 더 늘고, `[+kw]`는 키워드 인자(이름을 붙여 넘기는 값) 자리를 추가한다. 인자가 2개인 함수든 5개인 함수든, 같은 종류의 블록을 상황에 맞게 늘려 쓸 수 있다. (이 "늘어난 구조"는 3장에서 보듯 `fields`가 아니라 `extraState`에 저장된다.)

## 2.11 직렬화(serialization) — 블록을 저장 가능한 데이터로

- **쉬운 정의**: 화면에 놓인 블록 배치를 **JSON(제이슨, 데이터를 글자로 적는 표준 형식)**으로 바꿔 저장하고, 다시 그 JSON을 읽어 블록을 복원하는 일이다. 블록 ↔ JSON 왕복이다.
- **일상 비유**: 조립한 레고를 사진과 설명서로 남겨 두는 것. 나중에 그 설명서를 보면 똑같이 다시 조립할 수 있다.
- **BlockPy에서**: 워크스페이스의 블록 상태를 JSON으로 저장해 두었다가 파일로 불러오거나, 편집 도중 이전 배치를 그대로 되살리는 데 쓴다. 특히 파이썬으로 잠깐 갔다가 블록으로 돌아올 때, 구조가 바뀌지 않았다면 저장해 둔 블록 JSON을 그대로 복원해 **블록이 흐트러지거나 배치가 어긋나는 것을 방지**한다(3.4절의 "스냅샷 복구").

## 2.12 제너레이터(generator) — 블록을 코드로 번역하는 규칙

- **쉬운 정의**: 각 블록을 대응하는 **텍스트 코드로 바꾸는 변환 규칙**이다. 블록 → 코드 방향의 번역기라고 보면 된다.
- **일상 비유**: 그림 문자(픽토그램)를 보고 그 뜻을 문장으로 풀어 쓰는 통역과 같다. 표지판 하나하나에 "이건 이런 문장으로 읽는다"는 규칙이 정해져 있다.
- **BlockPy에서**: 모든 `ir_*` 블록에는 대응하는 파이썬 생성 규칙이 붙어 있어, 워크스페이스의 블록을 읽어 파이썬 코드로 내보낸다. **중요한 점은, 생성되는 파이썬이 오직 블록의 구조에서만 나온다는 것**이다. 블록의 색이나 라벨 같은 겉보기 정보는 결과 코드에 전혀 영향을 주지 않는다. 이것이 1장의 lowering 원칙이자, 아래 2.14와 3.6에서 자세히 다룰 "인식 ⟂ 번역 분리"다.

## 2.13 왜 블록코딩이 교육에 좋은가

블록코딩이 입문 교육에서 사랑받는 데는 분명한 이유가 있다.

- **낮은 바닥, 높은 천장(low floor, high ceiling)**: "바닥이 낮다"는 것은 처음 시작하기가 아주 쉽다는 뜻이고, "천장이 높다"는 것은 실력이 늘어도 계속 어려운 것을 만들 수 있다는 뜻이다. 블록은 문법 실수 없이 곧장 시작할 수 있으면서(낮은 바닥), 반복·조건·함수·라이브러리까지 얼마든지 쌓아 올릴 수 있다(높은 천장).
- **회상보다 인식(recall vs recognition)**: "회상"은 아무것도 없는 상태에서 스스로 떠올려 적는 것이고(빈 종이에 답 쓰기), "인식"은 보기 중에서 맞는 것을 알아보는 것이다(객관식 고르기). 글자 코딩은 명령어 철자를 **회상**해야 하지만, 블록코딩은 툴박스에 늘어놓인 블록 중에서 필요한 것을 **알아보고 고르기만** 하면 된다. 사람에게는 회상보다 인식이 훨씬 쉬우므로, 초보자의 부담이 크게 줄어든다.
- **말이 안 되는 상태를 막음**: 형태가 맞는 블록끼리만 연결되고 shadow 블록이 빈칸을 지켜 주므로, 프로그램은 늘 문법적으로 성립하는 상태를 유지한다. 학생은 "돌아가긴 하는데 뜻이 틀린" 논리 문제에만 집중할 수 있다.

## 2.14 BlockPy는 이 개념들을 어떻게 쓰는가

BlockPy는 위의 표준 블록 개념 위에 자기만의 세 가지 설계를 얹어, "블록으로 배우되 진짜 파이썬을 다룬다"는 목표를 이룬다. 여기서 나오는 용어(ir_call, recognition ⟂ lowering, 고정 블록)는 3장의 구현과 4장의 논문 기여에서 그대로 반복되므로 잘 익혀 두자.

- **`ir_*` 블록 — 파이썬 문법 그 자체를 블록으로**: BlockPy의 블록은 스크래치식 놀이 블록이 아니라, 파이썬의 **AST(추상 구문 트리) 노드 하나하나**에 대응한다. 이 블록들의 이름이 `ir_call`, `ir_if`처럼 `ir_`로 시작한다(IR = 중간 표현, 1장 참조). 파이썬에 존재하는 모든 문법 종류가 빠짐없이 블록으로 정의되어 있어(전수성), 어떤 파이썬 코드든 블록으로 바꿀 수 있다.

- **통합 `ir_call` — 함수 호출은 하나의 블록으로**: `print(...)`이든, `cv2.imread(...)`이든, 학생이 직접 만든 함수든, 함수를 "호출"하는 일은 전부 **하나의 통합된 `ir_call` 블록**으로 표현된다. 라이브러리별 블록들은 이 `ir_call` 위에 색과 이름표만 입힌 "겉껍질(skin)"이라, 겉모습이 달라도 실제로는 **똑같은 호출 코드로 번역**된다(1장의 lowering이 하나로 모인다는 이야기). 덕분에 새 라이브러리를 추가해도 번역 규칙을 새로 만들 필요가 없다.

- **인식과 번역의 분리(recognition ⟂ lowering)**: 이것이 BlockPy 설계의 핵심 안전장치다. "인식(recognition)"은 이 블록이 무슨 라이브러리의 무슨 함수인지 **알아채어 색과 라벨을 입히는** 겉보기 판단이고, "번역/로우어링(lowering)"은 블록을 실제 파이썬 코드로 **내려쓰는** 일이다. BlockPy에서는 생성되는 파이썬이 오직 블록의 구조에서만 나오고, 색·라벨·인식 결과 같은 표시 정보에서는 절대 나오지 않는다. 그래서 설령 인식이 틀려(엉뚱한 라이브러리로 잘못 색칠) 있어도, **왕복된 파이썬 코드는 결코 틀리지 않는다.** 잘못된 인식은 겉모습만 어색하게 할 뿐 프로그램의 뜻을 바꾸지 못한다. (4장은 이를 "건전성 정리"로 정식화한다.)

- **고정 블록 UX**: 함수·메서드·속성 이름은 수정 불가능한 라벨로 고정하고, 변수는 드롭다운으로만 고르게 하며, 자유 텍스트는 리터럴·식별자만 허용한다. 이 엄격함이 오히려 초보자를 지켜 준다. 이름을 오타 낼 여지가 없으니, 블록에서 만들어지는 파이썬은 언제나 문법적으로 올바르다.

정리하면, BlockPy는 블록코딩의 친절함(낮은 바닥, 인식 중심, 문법 오류 방지)을 그대로 누리면서도, 그 블록이 만들어 내는 결과물은 **타협 없는 진짜 파이썬 코드**가 되도록 설계되어 있다. 다음 장에서는 이 블록들이 실제로 파이썬과 어떻게 무손실로 오가는지, 그 내부 원리를 실제 코드와 함께 들여다본다.

# 3. BlockPy 구현 상세

앞의 두 장이 "무엇을·왜"였다면, 이 장은 "어떻게"다. 어렵게 느껴질 수 있으니, **딱 한 줄짜리 프로그램 `x = 3 + 4` 하나를 골라 처음부터 끝까지 따라간다.** 이 예시가 3.0에서 전체 그림을 보여주고, 이후 각 절이 그 여행의 한 구간씩을 확대해 실제 코드와 함께 설명한다. 코드를 건너뛰고 싶으면 각 절 앞의 **쉬운 설명** 회색 인용과 "예시" 상자만 읽어도 흐름을 잡을 수 있다.

## 3.0 한 프로그램의 여행: `x = 3 + 4` (미리보기)

> **비유.** 한국어를 아랍어로 오가는 통역소를 떠올리자(1장 IR). 한국어(파이썬 글자)를 곧장 아랍어(블록 그림)로 바꾸지 않고, 가운데 **영어(IR)**를 거친다. 아래는 `x = 3 + 4`라는 한 문장이 이 통역소를 한 바퀴 도는 모습이다. 각 단계의 **실제 데이터**를 그대로 보였으니, 세부는 몰라도 "글자 → 트리 → 블록 → 다시 트리 → 다시 글자"의 리듬만 느끼면 된다.

**① 파이썬 글자 (사용자가 친 것)**

```python
x = 3 + 4
```

**② 파싱 → IR (진짜 파이썬 `ast.parse`가 만든 트리를 JSON으로)**

`pythonToIR`을 거치면 위 한 줄이 이런 트리 모양 데이터가 된다. (읽는 법: `type`이 노드 종류, 나머지 칸이 그 자식이다.)

```json
{ "type": "Module", "body": [
  { "type": "Assign",
    "targets": [ { "type": "Name", "id": "x" } ],
    "value": { "type": "BinOp",
      "left":  { "type": "Constant", "value": 3 },
      "op":    { "type": "Add" },
      "right": { "type": "Constant", "value": 4 } } } ] }
```

말로 풀면 "**대입(Assign)**: 왼쪽은 변수 `x`, 오른쪽은 **덧셈(BinOp: Add)**인데 그 덧셈의 왼쪽은 **상수 3**, 오른쪽은 **상수 4**"다. 정확히 1장에서 그렸던 그 족보 트리다.

**③ IR → 블록 JSON (`irToBlockly`) → 화면 블록**

같은 트리를 이번엔 블록 조각으로 바꾼다. 실제로 나오는 데이터는 이렇다.

```json
{ "type": "ir_assign", "extraState": { "n": 1 },
  "inputs": {
    "TARGET0": { "block": { "type": "ir_name", "fields": { "ID": { "id": "x" } } } },
    "VALUE":   { "block": { "type": "ir_binop", "fields": { "OP": "Add" },
      "inputs": {
        "LEFT":  { "block": { "type": "ir_const", "fields": { "VALUE": "3" } } },
        "RIGHT": { "block": { "type": "ir_const", "fields": { "VALUE": "4" } } } } } } } }
```

`Assign` 노드가 `ir_assign` 블록으로, `BinOp`가 `ir_binop` 블록으로, `Constant 3/4`가 `ir_const` 블록으로 **하나씩 짝지어졌다**(2장의 `ir_*` 블록). 화면에서는 이렇게 보인다.

```
┌────────────────────────────────────────┐
│ [x ▾]  =  ( [3]  ➕ Add ▾  [4] )        │  ← ir_assign 안에 ir_binop, 그 안에 ir_const 둘
└────────────────────────────────────────┘
```

**④ 블록을 다시 파이썬으로 (`blocklyToIr` → `irToPython`)**

학생이 블록을 만지면 역방향이 돈다. 블록 JSON을 다시 IR(②와 **글자 하나 안 틀리고 같은 트리**)로 낮추고(lowering), 진짜 파이썬의 `ast.unparse`가 텍스트로 되돌린다.

```python
x = 3 + 4
```

출발점(①)과 도착점(④)이 같다. 이 "한 바퀴가 안 깨지는 것"이 BlockPy의 존재 이유이며(1장 왕복·무손실), 아래 절들이 이 여행의 각 구간을 실제 코드로 확대한다.

## 3.1 단일 IR의 선택: 왜 CPython `ast`인가

> **쉬운 설명.** 예전 BlockPy는 파이썬을 직접 파싱하는 손으로 짠 컴파일러를 썼다. 그런데 파이썬 문법 전체를 사람이 다시 구현하면 진짜 파이썬과 미묘하게 어긋나는 지점이 반드시 생긴다(예: `match`문, walrus `:=`). 그래서 "우리가 파이썬을 흉내 내지 말고, **진짜 파이썬에게 파싱을 시키자**"로 방향을 틀었다.

> **비유.** 프랑스 요리책을 쓸 때 프랑스어를 어설프게 아는 사람이 옮기면 틀린다. 아예 **프랑스인 셰프 본인**에게 레시피를 받아 적으면 원본과 어긋날 일이 없다. BlockPy는 "파이썬 셰프 본인"(CPython)에게 파싱과 코드 생성을 맡긴다.

IR의 정의는 `src/utils/pyAstBridge.js`에 있다. 직렬화 규칙(`_to_ir`)은 극도로 단순하다 — 모든 `ast.AST` 노드를 `{ "type": <노드클래스명>, <각 _fields...> }` dict로 바꾸는 게 전부다.

```python
def _to_ir(node):
    if isinstance(node, ast.AST):
        d = {"type": type(node).__name__}
        for f in node._fields:                            # 노드가 가진 모든 자식 칸을
            d[_key(f)] = _to_ir(getattr(node, f, None))   # 재귀적으로 변환
        ...
```

**예시.** 위 `Assign` 노드의 `_fields`는 `("targets", "value", "type_comment")`이다. 그래서 3.0의 ②에 `targets`와 `value`가 그대로 나타났다. 파이썬에 새 문법이 추가돼 노드에 칸이 늘어도, `node._fields`를 통째로 도는 이 코드는 **자동으로** 그 칸을 실어 나른다.

이 선택이 주는 결정적 성질이 **전수성(totality, 1장)**이다. 손으로 짠 파서는 "지원 문법 = 구현한 만큼"이지만, `node._fields`를 전부 도는 방식은 3.12 문법 전체를 이미 덮는다. `irToBlockly.js`의 `NODE_POLICY` 표가 모든 ast 노드 클래스를 빠짐없이 분류하고, `ir_coverage.spec.js`가 "빠진 노드/핸들러 없는 노드"를 기계로 잡는다. 미처리 노드 0 = **`raw=0`**. 그리고 텍스트를 만드는 유일한 주체가 진짜 `ast.unparse`이므로, 우리 IR이 올바른 트리이기만 하면 결과는 **항상 문법적으로 올바른 파이썬**이다.

## 3.2 무손실 계약과 그 증명

> **쉬운 설명.** "무손실"은 "블록으로 바꿨다 다시 파이썬으로 돌려도 뜻이 안 바뀐다"는 뜻이다(1장). 이걸 "글자가 똑같다"가 아니라 "**문법 트리가 똑같다**"로 정의한다. 들여쓰기·따옴표 스타일 같은 겉모습은 재생성되지만 의미는 보존된다.

> **비유.** 사진을 압축했다 푸는 것과 같다. 파일 크기(글자 배열)는 달라져도 그림(의미)이 하나도 안 흐려지면 "무손실"이다.

무손실 계약을 한 줄로: **`ast.dump(parse(원본)) == ast.dump(parse(재생성))`**.

**예시.** 사용자가 `3+4`(붙여 씀)를 넣었는데 BlockPy가 `3 + 4`(띄어 씀)로 되돌렸다고 하자. 글자는 다르다. 하지만 둘을 각각 다시 파싱하면 **똑같은 트리**(`BinOp(3, Add, 4)`)가 나오므로 `ast.dump`가 같고, 계약은 지켜진다. 반대로 `3 + 4`를 `3 - 4`로 되돌리면 트리가 달라지므로(`Add`≠`Sub`) 즉시 위반으로 잡힌다.

이 정의 위에서 `blocklyToIr.js`가 의도적으로 **버리는** 것들이 안전해진다:
- 이름의 `ctx`(Load/Store/Del)는 위치로 완전히 결정된다(대입 왼쪽=Store, 오른쪽=Load) → 안 실어도 재파싱하면 복원.
- `_loc`(줄·칸 위치)·`type_comment`는 의미가 아니라 위치/포맷이라 `ast.unparse`가 무시.

반대로 `ast.dump` 수준에서 **의미가 있는** 것(예: `u'abc'`의 `kind='u'` 접두)은 버리면 트리가 달라지므로, `ir_str`이 `extraState`에 실어 보존한다.

## 3.3 무손실을 완성하는 두 축: 상수 태깅과 주석 보존

> **쉬운 설명.** JSON은 파이썬의 모든 값을 그대로 담지 못하고, 주석은 트리에 원래 없다. 이 두 구멍을 메워야 진짜 무손실이 된다.

**(a) 상수 태깅 — `{"__py__": ...}` 꼬리표.**

> **비유.** 택배로 유리컵(까다로운 값)을 보낼 때 그냥 상자(JSON)에 넣으면 깨진다. "취급주의" 스티커를 붙이고 뽁뽁이로 싸는 것이 태깅이다.

가장 놀라운 예시가 **`1.0`**이다. 파이썬에서 `1.0`(실수)과 `1`(정수)은 다른 값인데, JSON을 통과하면 `1.0`이 정수 `1`로 **붕괴**해 버린다 — 무손실이 깨진다. 그래서 `_enc_float`는 정수값 실수를 꼬리표로 감싼다.

```python
def _enc_float(x):
    if x != x or x in (float('inf'), float('-inf')) or x.is_integer():
        return {"__py__": "float", "repr": repr(x)}   # 1.0 → {"__py__":"float","repr":"1.0"}
    return x
```

같은 방식으로 `bytes`→base64, `complex`→실수·허수 분해, `inf`/`nan`(JSON 토큰이 아님), `2^53`을 넘는 큰 정수(JS `JSON.parse`가 반올림)를 태깅한다. 원시값은 절대 평범한 dict가 아니고 ast 노드는 항상 `"type"`을 가지므로, `"__py__"` dict는 헷갈릴 일 없이 식별된다. 블록 면 표시는 `pyConstText`가, 역파싱은 `pyConstValue`가 맡아 **서로 정확한 역함수**다.

**(b) 주석 보존 — "Option 3".**

> **비유.** 트리(족보)에는 "이 사람 착함" 같은 **메모** 칸이 없다. 그래서 메모를 따로 옮겨 적고(추출), 각 메모가 누구 옆에 있었는지 기록했다가(귀속), 족보를 다시 글로 풀 때 제자리에 붙인다(재삽입).

주석은 ast에 없으므로 stdlib `tokenize`로 별도 추출하고(`_collect_comments`), `_attach_comments`가 각 주석을 가장 가까운 **문 노드**에 `_comments {leading[], trailing, after[]}`로 붙인다.

**예시.**

```python
x = 3   # 시작값     ← 인라인 주석: x=3 문의 trailing
# 결과 출력          ← 독립 주석: 다음 문의 leading
print(x)
```

역방향은 `ast._Unparser`를 상속한 `_CommentUnparser`가 재삽입하되, `elif` 붕괴나 docstring처럼 우회 경로까지 명시적으로 처리해 이중 방출·누락을 막는다. 포맷은 재생성하되 **주석 텍스트는 무손실**이라는 것이 "Option 3"이다.

## 3.4 방향 1: 파이썬 → 블록 (`syncCodeToBlocks`)

> **쉬운 설명.** 사용자가 파이썬을 치고 "변환"을 누르면 이 경로가 돈다: 파싱 → IR → 블록 JSON → 화면. 3.0의 ①→②→③ 구간이다.

전 과정은 `src/App.jsx`의 `syncCodeToBlocks(currentCode)`가 지휘한다(async — 파싱이 Pyodide에서 돈다). 핵심은 **핸들러 표**다. `irToBlockly.js`의 `EXPR_HANDLERS`/`STMT_HANDLERS`가 "노드 종류 → 블록 만드는 법"을 한 줄씩 적어 둔 사전이고, `exprToBlock`/`stmtToBlock`이 이 표를 보고 재귀적으로 내려간다.

**예시 — 실제 핸들러 세 줄.** 3.0의 `BinOp`·`Name`·`Constant`가 블록이 된 근거다.

```js
// irToBlockly.js — 노드를 블록 JSON으로 "쓴다"
BinOp:    (n) => blk('ir_binop', { OP: n.op.type },
            { LEFT: { block: exprToBlock(n.left) }, RIGHT: { block: exprToBlock(n.right) } }),
Name:     (n) => blk('ir_name', { ID: { id: n.id } }),
Constant: (n) => (typeof n.value === 'string'
            ? blk('ir_str', { TEXT: n.value })
            : blk('ir_const', { VALUE: pyConstText(n.value) })),   // 3 → "3"
```

읽는 법: `BinOp` 노드가 오면 `ir_binop` 블록을 만들고, 연산자 종류(`Add`)를 `OP` 필드에 넣고, 왼쪽·오른쪽 자식을 **다시 `exprToBlock`으로** 블록화해 `LEFT`/`RIGHT`에 끼운다. 이 재귀가 3.0 ③의 중첩 구조를 그대로 만든다.

`syncCodeToBlocks`가 변환 앞뒤로 챙기는 실무:
- **스냅샷 복구(빠른 길).** 텍스트가 직전 블록 편집과 **바이트 동일**하면 저장해 둔 워크스페이스 JSON을 그대로 복원한다 — 재파싱 없음, 블록 위치 안 흔들림(2.11).
- **스냅샷 복구(느린 길).** 텍스트는 바뀌었어도 `pythonToIR` 결과가 이전과 **IR 동일**(`_comments` 포함)이면 포맷·주석만의 편집이므로 레이아웃을 유지한다. (과거 정규식 문자열 비교는 "재들여쓰기"—파이썬에선 의미가 있음!—를 "변화 없음"으로 오판했는데, AST 동일성은 그런 의미 편집을 절대 놓치지 않는다.)
- **인식 오라클(표시 전용, 15초 예산).** `autoBlockifyRefs`(라이브러리 심볼을 툴박스에 물림)+`inferTypes`(Jedi 수신자 타입)로 블록을 **색칠**한다. 예산 초과 시 제네릭 색으로 즉시 진행하고, 오라클이 늦게 오면 `recolorLibBlocks`로 자가 치유한다. **왕복 파이썬은 불변**(§3.6).
- **fail-loud.** 핸들러 없는 노드는 `noHandler`가 조용히 틀리지 않고 예외를 던진다(1장).

## 3.5 방향 2: 블록 → 파이썬 (`blocklyToIr`) — 3.4의 거울상

> **쉬운 설명.** 사용자가 블록을 만지면 이 경로가 돈다: 블록 JSON → IR → 진짜 파이썬 텍스트. **이쪽이 "생성된 파이썬의 유일한 진실 원본"이다**(1장 lowering).

가장 아름다운 점은 이 방향이 3.4의 **정확한 거울상**이라는 것이다. 3.4가 "노드→블록을 **쓰는**" 핸들러였다면, 여기 `BLOCK_TO_EXPR`/`BLOCK_TO_STMT`는 "블록→노드를 **읽는**" 핸들러다.

**예시 — 아까 그 세 줄의 거울상.**

```js
// blocklyToIr.js — 블록을 노드로 "읽는다" (3.4의 반대)
ir_binop: (b) => ({ type: 'BinOp', left: blockToExpr(b.inputs.LEFT.block),
             op: { type: b.fields.OP }, right: blockToExpr(b.inputs.RIGHT.block) }),
ir_name:  (b) => ({ type: 'Name', id: /* b.fields.ID → 변수 이름 */ }),
ir_const: (b) => ({ type: 'Constant', value: pyConstValue(b.fields.VALUE) }),   // "3" → 3
```

3.4의 `BinOp` 핸들러와 나란히 놓으면 `OP` 필드, `LEFT`/`RIGHT` 입력이 **정확히 대칭**이다. `pyConstText`(3→"3")와 `pyConstValue`("3"→3)가 역함수인 것도 여기서 드러난다. 이 대칭이 무손실(3.2)을 코드 구조로 보장한다.

블록→파이썬에서 챙기는 실무:
- **깊은 복제.** `blocklyToIr`는 스냅샷을 **깊게 복제**한 뒤 작업한다. shadow 기본값을 in-place로 붕괴시키므로, 복제 안 하면 스냅샷 복구 사이클에서 기본값이 실제 블록으로 굳는다(2.8 shadow의 함정).
- **여러 스택·bare 표현식.** 캔버스의 모든 최상위 스택을 순회한다. 값 블록(`ir_binop` 등)이 홀로 놓이면 파이썬 규칙대로 `Expr` 문으로 감싼다.
- **fail-loud 검증자(교육용 필수).** 함수 이름칸에 `내 함수`(공백)를 넣으면 `checkName`이, `import a; import b`처럼 세미콜론을 넣으면 `fieldToAliases`가 verbatim 방출을 막고 명시적 에러를 낸다(2.9).
- **필수 본문.** 파이썬은 빈 본문을 허용하지 않으므로 `stmtListOrPass`가 빈 `if`/`for` 본문에 `pass`를 합성한다.

## 3.6 recognition ⟂ lowering: 코드 수준의 분리 (건전성 정리)

> **쉬운 설명.** 블록의 "색"과 블록이 만드는 "코드"는 **완전히 다른 데서** 나온다. 색은 "이 호출이 알려진 라이브러리인가" 같은 추측(introspection, Jedi, AI)에서 나오고, 코드는 오직 블록 구조(`extraState`)에서만 나온다. 그래서 추측이 틀려도 **색만 틀릴 뿐 코드는 절대 안 바뀐다.** 안전성의 핵심이자 4장 기여 ②다.

> **비유.** 형광펜으로 교과서에 밑줄을 긋는다고 문장 **내용**이 바뀌지 않는다. 밑줄(색=인식)을 엉뚱한 데 그어도 글자(코드=lowering)는 그대로다. BlockPy의 인식 오라클은 "밑줄 긋는 사람"일 뿐 "글을 고치는 사람"이 아니다.

**예시로 대비.** 사용자가 `image.resize(100, 100)`을 변환했다고 하자.
- **오라클이 맞힐 때**: "아, `image`는 PIL 이미지구나" 하고 블록을 에메랄드색으로 칠하고 파라미터 이름표(`size`)를 붙인다.
- **오라클이 틀릴 때**: 라이브러리를 몰라 블록을 회색으로 둔다.
- **두 경우 모두** 블록을 다시 파이썬으로 내리면 결과는 **똑같이** `image.resize(100, 100)`. 색·이름표는 달랐지만 코드는 한 글자도 안 변했다.

**코드 수준에서 왜 그런가.** 생성(lowering)은 `blocklyToIr.js` 핸들러만 결정하고, 오직 `extraState`와 입력 블록에서만 파이썬을 만든다:

```js
// ir_call: 색·라벨·인식여부는 여기 "일절 등장하지 않는다"
const fn = b.extraState && b.extraState.funcName;                 // 구조에서만
func = String(fn).includes('.') ? dottedToExpr(fn) : { type: 'Name', id: fn };
return { type: 'Call', func, args, keywords };
```

반면 색칠은 `libRegistry.js`의 `findLibCall`/`findConst`/`findAttr`가 하는데, **표시용 조회일 뿐** 위 계산에 끼어들지 않는다. 특정 라이브러리용 "스킨 블록"조차 `lowerLibBlock`이 **일반 `ir_call`과 동일한 Call IR**로 내린다. 따라서 인식은 표시를 승격할 뿐 코드를 못 바꾼다 — 이것이 **건전성(soundness) 정리**다.

## 3.7 임의 라이브러리 introspection → 블록 (하드코딩 이름표 없음)

> **쉬운 설명.** "cv2는 이렇게, numpy는 저렇게"라고 손으로 적은 표는 **없다**(프로젝트 강제 원칙). 대신 진짜 파이썬 프로세스가 그 라이브러리를 `inspect`로 들여다보고, 무엇이 함수·클래스·메서드·상수·속성인지 스스로 알아낸다.

> **비유.** 새 가전이 오면 설명서를 미리 외우는 게 아니라 제품을 **직접 열어 보고** 버튼이 몇 개인지 센다. `_inspect.py`가 라이브러리를 "열어 보는" 일을 한다.

**예시 — pyserial 블록화 과정.**

**(a) `_inspect.py` → LibrarySpec.** 별도 python 서브프로세스가 `serial.tools.list_ports`를 임포트해 `inspect`로 순회하며 이런 스펙을 만든다.

```json
{ "module": "serial.tools.list_ports",
  "entries": [
    { "kind": "function", "name": "comports",
      "params": [ { "name": "include_links", "kind": "positional", "hasDefault": true } ],
      "returns": true, "qualName": "serial.tools.list_ports.comports" },
    { "kind": "function", "name": "grep" },
    { "kind": "function", "name": "main" } ] }
```

포착 범위가 넓다: `_is_call`은 `inspect.isfunction`이 놓치는 **C 루틴**(`method_descriptor` 등)까지 잡고, `_instance_attrs`는 **`__init__`의 `self.x =`를 (실행하지 않고) AST로 파싱**해 `ListPortInfo.device` 같은 인스턴스 속성까지 찾는다. **하드코딩이 없다** — `_dist_to_import`가 pip 배포명 `pyserial`을 `importlib.metadata`로 **런타임 해석**해 실제 임포트명 `serial`을 얻는다(표가 아니다).

**(b) 서버 노출.** `server.js`의 `POST /api/blockify`가 이 스크립트를 spawn(win32 트리 종료·60초 타임아웃·블로킹 임포트 방어)해 결과를 준다.

**(c) LibrarySpec → 레지스트리 스펙.** `libImport.js`의 `librarySpecToRegistrySpecs`가 번역한다.
- **메서드 → 수신자 모델**: `Serial.write` → `serial.write`, 수신자 변수가 제목 접두이자 `argNames[0]` → `<recv>.write(...)`로 lower.
- **바인딩 별칭**: `import numpy as np`면 `np.mean`으로 렌더(그냥 `numpy.mean`으로 렌더하면 드래그 시 NameError).

**(d) 레지스트리 & 툴박스.** `registerLibBlock`은 `staticCheck`(식별자·중복 검증)를 통과한 스펙만 받고, `irToolbox.js`가 이를 `categoryToolbox` JSON으로 합성한다(패키지별 탭, 카테고리 색). 각 필수 입력에는 **드래그 즉시 유효 파이썬**이 되도록 shadow 기본 자식을 단다(2.8) — 그래서 골든패스에서 `list_ports.comports()`를 툴박스에서 끌어내자마자 유효한 파이썬이 나왔다.

## 3.8 Curate: 큐레이션(추상화/감축)

> **쉬운 설명.** 수천 개 API를 가진 거대 라이브러리를 학생에게 다 보여주면 압도당한다(2.13 "낮은 바닥"). Curate는 초/중/고 수준별로 작은 교육용 블록셋만 골라 별도 ★ 탭으로 보여준다. 새 코드 생성 방식이 아니라 **기존 블록들 위의 "뷰"**다.

> **비유.** 백과사전 전체를 초등학생에게 던지지 않고, "오늘 수업에 필요한 5쪽"만 뽑아 스티커를 붙여 준다. 원본 백과사전(전체 라이브러리 탭)은 그대로 있다.

- **AI 경로**: `POST /api/abstract-library`가 introspected 스펙(=진실)+목적을 MiniMax에 주되, 모델은 **정수 인덱스로만** entry를 고른다(이름을 지어내지 못하게). 서버가 환각 ref를 버리므로 시그니처는 항상 introspection에서 온다.
- **오프라인 휴리스틱**: `curateHeuristic.js`가 **AI 없이 같은 응답 형태**를 낸다. 신호는 전부 구조적이다 — 인자 수 적음, 동사형 이름(범용 영어 동사 관례이지 라이브러리별 표가 아님), 문서 존재, 사용자 목적어와의 키워드 겹침.
- **2단 점진 공개**: `tier: idx < cap ? 'core' : 'more'` — 핵심 세트를 앞에, 나머지는 접힌 "더 보기" 서랍에. **예시(골든패스 실측)**: `serial`을 같은 목적으로 큐레이트하면 초등 core=5개 < 고등 core=22개, 그리고 초등 core ⊆ 고등 core(레벨이 오르면 더 드러날 뿐 사라지지 않음).
- **★ 뷰**: `addCuration`은 이미 등록된 블록 타입들의 부분집합을 **참조**할 뿐 스펙을 복제하지 않는다. 큐레이션은 등록 타입 위의 VIEW이지 새 lowering이 아니므로 §3.6의 건전성이 그대로 유지된다.

# 4. 연구/논문 프레이밍

3장까지가 "BlockPy가 어떻게 동작하는가"였다면, 이 장은 그것을 **학술적 기여의 언어로 다시 쓰는** 부분이다. 먼저 블록↔텍스트 변환이라는 문제를 무손실성(losslessness)과 확장성(extensibility)의 긴장 위에서 정의하고(4.1), 그 위에서 BlockPy의 신규 기여를 네 갈래로 명확히 한 뒤(4.2), 기존 시스템들과 대비하여 차별점을 드러낸다(4.3). 이어서 각 기여를 검증하는 평가 방법론을 제안하고(4.4), 마지막으로 투고 가능한 논문 제목과 초록 초안을 제시한다(4.5). 3장의 함수·테스트 자산이 여기서 그대로 평가 프로토콜의 근거가 된다.

---

## 4.1 문제 정의: 왜 블록↔텍스트 변환에서 무손실성과 확장성이 동시에 어려운가

블록 기반 프로그래밍 환경과 텍스트 코드 사이의 변환은 오래된 목표이지만, 두 요구를 **동시에** 만족시키려 할 때 본질적인 긴장이 발생한다.

**(1) 무손실성(losslessness)의 어려움 — 표현력 불일치와 정규형의 부재.**
블록 표현과 텍스트 표현은 표현할 수 있는 프로그램의 집합이 서로 다르다. 실용적인 텍스트 언어(Python)는 리스트 컴프리헨션, 데코레이터, 별표 언패킹, 조건식(삼항), 비트 연산 등 문법적으로 풍부한 구성을 가진다. 블록 환경이 이 구성들의 부분집합만 모델링하면, "블록으로 표현 불가능한 코드"가 필연적으로 생기고 변환은 **부분 함수**가 된다. 더 근본적인 문제는 **왕복(round-trip)의 정합성**이다. 텍스트 → 블록 → 텍스트를 거쳤을 때 원본과 "같은" 프로그램이 나온다는 것을 어떻게 정의하고 보장할 것인가? 문자열 동일성은 지나치게 강하고(공백·괄호·따옴표 스타일 차이에 취약), "대충 같아 보임"은 지나치게 약하다. 대다수 시스템은 자체적으로 만든 근사 AST 또는 블록 JSON을 중간 표현으로 쓰는데, 이 중간 표현은 진짜 언어의 의미론과 **검증 가능한 방식으로 연결되어 있지 않다.** 그 결과 무손실성은 "우리가 테스트해 본 예제에서는 대체로 유지된다"는 경험적 주장에 머문다.

**(2) 확장성(extensibility)의 어려움 — 라이브러리 롱테일과 수작업 병목.**
교육용이든 실무용이든, 학습자가 실제로 쓰고 싶어 하는 것은 언어 코어가 아니라 **라이브러리**다(OpenCV, requests, pandas, matplotlib, 그리고 무엇보다 교사가 직접 만든 로컬 모듈). 그런데 라이브러리는 사실상 무한한 롱테일을 이룬다. 함수·클래스·메서드·속성·상수가 수백~수천 개이고, 버전마다 시그니처가 바뀐다. 기존 블록 환경은 각 라이브러리를 **손으로** 블록화한다. 이는 (i) 확장이 사람의 노동에 선형 비례하고, (ii) 라이브러리 버전과 블록 정의가 필연적으로 어긋나며, (iii) 교사가 만든 임의의 `.py` 모듈은 사실상 지원 불가라는 세 가지 병목을 낳는다.

**(3) 결정적으로, 무손실성과 확장성은 서로를 침식한다.**
확장성을 얻으려고 "인식(recognition)"—즉 이 호출이 `cv2.imread`인지, 이 변수가 어떤 타입인지 추론하는 로직—을 도입하면, 그 추론이 틀렸을 때 **생성되는 코드까지 오염될** 위험이 생긴다. 인식은 본질적으로 불완전한(휴리스틱·정적 타입추론·AI) 신호에 의존하는데, 이 신호가 코드 생성 경로에 개입하는 순간 무손실성은 "오라클의 정확도"에 인질로 잡힌다. 반대로 무손실성을 지키려고 표현을 언어 코어로 좁히면 확장성을 잃는다. **본 연구의 문제의식은 바로 이 긴장을 구조적으로 해소하는 것이다.**

---

## 4.2 BlockPy의 신규 기여

BlockPy는 위 긴장을, 네 개의 서로 맞물린 설계 결정으로 해소한다. (각 기여는 3장의 구현 절과 1:1로 대응한다.)

### 기여 ① 진짜 언어의 AST를 단일 정규 IR로 삼아 무손실성을 *증명 가능*하게 만든다 (↔ §3.1–3.3)

BlockPy의 중간 표현(IR)은 자체 설계한 근사 트리가 아니라 **CPython 3.12의 `ast` 그 자체**다. Python → IR 변환은 Pyodide(브라우저 내 WASM Python) 안에서 `ast.parse`를 호출하고, 각 노드의 `_fields`를 전부 JSON으로 직렬화한다. JSON으로 표현할 수 없는 상수—`bytes`, `complex`, `inf`/`nan`, 2⁵³을 넘는 정수, 정수값을 갖는 float(`1.0`) 등—는 `{__py__: ...}` 태그로 보존한다. IR → Python 변환은 JSON에서 `ast` 노드를 재구성한 뒤 `ast.unparse`로 되돌린다.

이 설계의 핵심 이점은 무손실성이 **경험적 주장이 아니라 형식적 계약**이 된다는 데 있다. 왕복의 정합성을 다음 등식으로 정의한다.

> **AST 동일성 계약:** `ast.dump(ast.parse(원본)) == ast.dump(ast.parse(재생성))`

즉 원본과 재생성 코드는 문자열로서가 아니라 **파싱 후 AST로서 동일**해야 한다. 이는 공백·괄호·따옴표 스타일 같은 무의미한 차이를 정확히 추상화하면서, 의미를 바꾸는 모든 차이는 포착하는 올바른 동치 관계다. 진짜 언어의 파서/언파서를 IR의 양 끝에 둠으로써, 우리는 "우리 블록이 Python을 얼마나 잘 흉내 내는가"라는 근사 문제를, "왕복이 AST를 보존하는가"라는 **판정 가능한 등식**으로 환원한다. 주석은 정보 손실 없이 다루기 위해 stdlib `tokenize`로 추출하여 해당 IR 노드에 `_comments`로 귀속시키고(포맷 자체는 재생성), `_CommentUnparser` 서브클래스가 언파스 시 재삽입한다.

### 기여 ② recognition ⟂ lowering 분리 — 표시/인식을 건전한 lowering과 분리하여, 휴리스틱·AI 오라클이 코드를 절대 오염시키지 못하게 한다 (↔ §3.6)

이것이 본 연구의 **건전성(soundness) 정리**이자 핵심 신규성이다. BlockPy는 두 관심사를 아키텍처 수준에서 직교(orthogonal)하게 분리한다.

- **lowering(하강):** 블록 → IR → Python. 블록이 생성하는 Python은 **오직 블록의 구조와 `extraState`(모듈·함수·인자)에서만** 나온다. `blocklyToIr.js`가 각 `ir_*` 블록을 `ast` 노드로 lower하며, 이것이 생성 코드의 **유일한 진실 원본(single source of truth)**이다.
- **recognition(인식):** introspection, Jedi 타입추론, 휴리스틱, AI 큐레이션 등. 이들은 블록을 **색칠하고 라벨을 붙이는 표시(display) 메타데이터**만 만든다.

이 두 경로는 데이터 흐름상 만나지 않는다. 표시 메타데이터는 lowering 함수의 입력이 아니다. 따라서 다음 명제가 성립한다.

> **건전성 정리(비형식):** 인식 오라클은 블록을 *잘못 칠할(mis-color)* 수만 있고, 왕복되는 Python을 *바꿀 수는 없다.* 틀린 오라클은 표시상 무해하다.

이 분리는 실무적으로 매우 강력한 함의를 가진다. 우리는 라이브러리 인식·타입추론·AI 추상화 같은 **본질적으로 불완전한** 기법을 마음껏 쓸 수 있다. 그것들이 최악의 경우 하는 일은 블록 색을 틀리게 하는 것뿐이며, 학습자가 실행하는 코드의 정확성은 손상되지 않기 때문이다. 등록된 라이브러리 블록(Tier-A/Tier-B)조차 통합 `ir_call` 위의 "스킨"에 불과하여, 인식되지 않은 일반 `ir_call`과 **동일한 Call IR로 lower**된다. 인식은 표시를 승격(promote)할 뿐 lowering을 바꾸지 않는다. 정밀 속성 색칠을 위한 타입추론(Tier-1 결정론적, Tier-2 Jedi 정적 분석 — 실행하지 않음)도 전적으로 표시 전용이다.

### 기여 ③ 런타임 introspection 기반 임의 라이브러리 블록화 + 초/중/고 점진 공개 교육 큐레이션 (↔ §3.7–3.8)

확장성 병목을 BlockPy는 **하드코딩된 이름표 없이** 해소한다. `_inspect.py`가 별도 Python 서브프로세스에서 `inspect`를 돌려, **임의의 pip 라이브러리 또는 로컬 `.py` 모듈**로부터 `LibrarySpec`을 생성한다. 각 항목(entry)은 `{kind, name, owner, params, returns, doc, qualName}`을 담으며, C로 구현된 메서드, static/classmethod, 속성(`__init__`의 `self.x =`를 AST로 파싱하여 포착), 모듈 상수까지 잡아낸다. 배포명(dist name)에서 임포트명으로의 매핑은 **표를 두지 않고** `importlib.metadata`로 런타임 해석한다(프로젝트 메모리의 "하드코딩 라이브러리 표 금지" 원칙과 정합). `libImport`가 `LibrarySpec`을 레지스트리 스펙으로 매핑하며(메서드는 receiver 모델), 레지스트리의 `findLibCall`/`findConst`/`findAttr`는—기여 ②의 원칙대로—블록을 **색칠만** 한다.

그 위에 교육적 **큐레이션(curation)** 층을 얹는다. 거대한 라이브러리 API를 초급/중급/고급 레벨별 작은 블록셋으로 감축하고, 2단 점진 공개(core + "더 보기")로 인지 부하를 조절한다. 큐레이션은 AI(MiniMax; 인덱스 기반 환각 방지, 매크로 arity 검증)로 하거나 결정론적 오프라인 휴리스틱으로 한다. 매크로는 합성된 `ir_*` 트리다. 결정적으로, **큐레이션은 등록 타입 위의 VIEW(★ 탭)이지 새로운 lowering이 아니다** — AI가 개입해도 기여 ②에 의해 생성 코드는 오염되지 않는다.

### 기여 ④ 전수성(totality, raw=0) — 기계 검증된 완결성 (↔ §3.1, §3.10)

무손실성이 "실제로" 성립하려면 IR → Blockly 변환이 **모든** 노드를 다뤄야 한다. BlockPy의 `irToBlockly.js`는 `NODE_POLICY`를 통해 CPython 3.12의 **전체** `ast` 노드 집합을 분류하며, 미분류(raw) 노드 수가 0임을 `ir_coverage.spec.js`가 기계적으로 검증한다(**raw=0 전수성**). 미지의 노드를 만나면 조용히 틀리는 대신 **fail-loud**(`noHandler`)로 즉시 실패한다. 역방향(`blocklyToIr.js`)도 마찬가지로, `ir_*`가 아닌 블록을 만나면 throw한다. 이 "조용히 틀리지 않는다(never silently wrong)" 규율 덕분에, 커버리지 공백은 런타임에 명시적 오류로 드러나며 무손실성 계약의 사각지대가 생기지 않는다.

## 4.3 관련 연구와의 비교

BlockPy의 차별점은 세 축—**진짜 언어의 AST를 IR로 사용**, **증명 가능한 무손실성**, **임의 라이브러리 블록화**—으로 요약된다. 주요 선행 시스템과 대비한다.

| 시스템 | 텍스트↔블록 접근 | 중간 표현 | 무손실 왕복 | 라이브러리 확장 | BlockPy와의 차이 |
|---|---|---|---|---|---|
| **MakeCode** | 텍스트 우선, `//%` 주석으로 블록 메타 부여 | TypeScript AST(내부) + 블록 매핑 | 부분적(지원 구성 한정) | **타깃별 수제** API 어노테이션 | BlockPy는 어노테이션 없이 런타임 introspection으로 임의 라이브러리를 블록화하고, AST 동일성으로 무손실을 형식화 |
| **Scratch / mBlock** | 텍스트 표현 없음, 확장은 고정 블록 | 자체 블록 모델 | 해당 없음(텍스트 부재) | **고정 확장 블록** 수작업 | BlockPy는 진짜 텍스트 언어(Python)와 양방향, 롱테일 라이브러리 자동화 |
| **App Inventor** | 블록 전용, 컴포넌트 기반 | 컴포넌트/블록 모델 | 해당 없음 | 미리 정의된 **컴포넌트** | BlockPy는 범용 Python + 임의 모듈, 텍스트 왕복 보장 |
| **Blockly(일반)** | 코드 생성기(단방향이 일반적) | 블록 JSON | 역방향(코드→블록) 미보장 | 개발자가 블록 정의 수제 | BlockPy는 Blockly 위에서 진짜 `ast`를 IR로 삼아 역방향까지 무손실 |
| **Pencil Code / Droplet** | **줄(line) 기반** 텍스트↔블록 편집 | 편집기 파스트리(CoffeeScript/JS) | 표면 구문 보존 지향 | 언어 코어 중심 | BlockPy는 줄 매핑이 아니라 노드 전수 매핑 + AST 동일성 계약, 라이브러리 확장이 1급 목표 |
| **Hedy** | **단계별(gradual) 언어**로 점진 학습 | 단계별 문법 | 단계 전이(변환) | 언어 자체를 단계화 | BlockPy는 언어를 바꾸지 않고 진짜 Python을 유지, 대신 큐레이션(★ VIEW)으로 점진 공개 |

핵심 대비를 문장으로 정리하면 다음과 같다. MakeCode는 BlockPy와 철학적으로 가장 가깝지만(텍스트 우선, 어노테이션), 그 어노테이션이 **타깃별 수제**라는 점에서 임의 라이브러리 확장성이 원리적으로 제한된다. Droplet/Pencil Code는 줄 단위 표면 구문 매핑으로 편집 경험은 매끄럽지만, **노드 전수성**과 **AST 동일성 무손실 계약**을 형식적으로 내세우지 않으며 라이브러리 롱테일은 목표가 아니다. Hedy는 점진성을 **언어를 단계적으로 바꿔** 달성하는 반면, BlockPy는 언어를 진짜 Python으로 고정한 채 큐레이션을 표시 층에 둔다(기여 ②의 직교성 덕분에 가능). **BlockPy만이 "진짜 언어의 AST = IR"라는 결정과 "recognition ⟂ lowering" 분리를 결합하여, 무손실성을 증명 가능하게 유지하면서 임의 라이브러리로 확장한다.**

## 4.4 평가 방법론

기여 ①~④는 서로 다른 종류의 주장이므로, 평가도 다층으로 설계한다. BlockPy는 이미 상당한 검증 자산(IR 186 테스트, 퍼즈, 187 코퍼스, 골든패스 E2E, gen 31 — 모두 3.10 표에 정리됨)을 갖추고 있어 이를 학술 평가 프로토콜로 재구성할 수 있다.

**(1) 전수성(totality) 평가 — 기여 ④.**
`ir_coverage.spec.js`류의 기계 검증으로 CPython 3.12 `ast` 노드 집합에 대한 커버리지가 raw=0임을 확인한다. 보고 지표: 처리 노드 종류 수 / 전체 노드 종류 수 = 100%, fail-loud 경로가 미처리 노드에서 실제로 발화하는지의 음성(negative) 테스트.

**(2) 왕복 정합성(round-trip) 평가 — 기여 ①.**
AST 동일성 계약 `ast.dump(parse(원본)) == ast.dump(parse(재생성))`을 판정 함수로 삼아, 세 개의 프로그램 모집단에 적용한다: (a) 손으로 만든 IR 게이트 186 테스트, (b) node + CPython 코퍼스 187 케이스, (c) 실제 라이브러리 사용 예제. 지표: AST 동일 왕복 통과율(목표 100%), 실패 시 최소 반례 자동 축소(shrinking).

**(3) 퍼즈(fuzz) 평가 — 기여 ①·④의 결합.**
프로그램 생성기로 무작위/문법 유도 Python을 생성하여 Python→IR→Python 왕복의 AST 동일성을 대량 검사한다. 지표: 퍼즈 케이스 수 대비 통과율, 발견된 반례의 노드 종류 분포. 퍼즈는 커버리지 표에 빠진 실전 조합을 드러내는 역할을 한다.

**(4) 건전성(soundness) 평가 — 기여 ②.**
이 정리를 실증하는 **오라클 교란(oracle-perturbation) 실험**을 제안한다: 인식 오라클(라이브러리 매칭, Jedi 타입추론, AI 큐레이션)을 의도적으로 틀리게(무작위 색칠, 오분류) 주입한 뒤, **생성되는 Python이 오라클 교란과 무관하게 불변임**을 AST 동일성으로 확인한다. 이는 "틀린 오라클은 표시상 무해"라는 명제의 직접적 실험적 증거가 된다. 지표: 오라클 정확도를 0%까지 낮춰도 코드 생성 왕복 통과율 100% 유지.

**(5) 라이브러리 블록화 평가 — 기여 ③.**
임의의 pip 라이브러리·로컬 모듈 표본에 introspection을 적용하여 (i) `LibrarySpec` 생성 성공률, (ii) 생성된 모든 호출이 **구문적으로 유효한 Python**인지의 검증률(blockpy-gen의 정적 검사), (iii) 시그니처 충실도(introspect한 params가 실제 API와 일치하는가)를 측정한다.

**(6) 골든패스 E2E — 제품 무결성.**
데스크톱/브라우저 실제 UI에서 대표 시나리오(입력→변환→블록 렌더→실행)를 종단 검증한다(골든패스 E2E, gen 31 자산 재사용).

**(7) 사용자 연구(제안).**
형식적 평가와 별도로, 교육 효과·사용성 가설을 검증하는 통제 연구를 제안한다.
- *가설 H1(양방향 학습 전이):* 블록↔텍스트를 자유 왕복할 수 있을 때, 학습자의 블록→텍스트 전이(순수 텍스트 코딩으로의 이행)가 단방향 환경보다 빠르다.
- *가설 H2(임의 라이브러리 접근성):* 교사가 만든 로컬 모듈을 즉시 블록화할 수 있으면, 준비 시간과 학습자 과제 완수율이 개선된다.
- *가설 H3(점진 공개):* 초/중/고 큐레이션 2단 공개가 전량 노출 대비 인지 부하(자기보고 + 과제 시간)를 낮춘다.
- 설계: 피험자 내/간 혼합, 사전-사후 코딩 평가 + NASA-TLX 인지부하 + 왕복 오류율 로그. 참가자: 중·고교 및 학부 입문 학습자.

## 4.5 논문 제목·초록 초안

**가제(택1)**
- *A Real-AST Canonical IR for Provably Lossless, Extensible Block↔Text Programming*
- 국문: **진짜 AST를 정규 IR로: 증명 가능한 무손실·확장형 블록↔텍스트 변환**

**초록 초안**

> 블록 기반 프로그래밍 환경은 입문 학습자의 진입 장벽을 낮추지만, 실제 텍스트 언어와의 **무손실 양방향 변환**과 **임의 라이브러리로의 확장**을 동시에 달성하기 어렵다. 확장성을 위해 "이 호출이 무엇인가"를 인식(recognition)하려는 순간, 그 인식의 불완전성이 생성 코드의 정확성을 위협하기 때문이다. 본 논문은 이 긴장을 구조적으로 해소하는 시스템 BlockPy를 제안한다. 핵심 설계는 세 가지다. 첫째, 자체 근사 트리 대신 **진짜 언어의 AST(CPython 3.12 `ast`)를 단일 정규 IR**로 사용하여, 무손실성을 경험적 주장이 아니라 판정 가능한 등식 `ast.dump(parse(원본)) == ast.dump(parse(재생성))`—즉 **AST 동일성 왕복 계약**으로 형식화한다. 둘째, **recognition ⟂ lowering 직교성**을 아키텍처 불변식으로 강제한다: 블록이 생성하는 Python은 오직 블록 구조와 상태에서만 나오고, 인식(introspection·정적 타입추론·AI 큐레이션)은 표시 메타데이터만 만든다. 이로부터 **건전성 정리**—틀린 오라클은 블록을 잘못 칠할 수만 있고 코드를 바꿀 수 없다—가 따르며, 우리는 이를 오라클을 의도적으로 교란해도 코드 왕복이 불변임을 보이는 실험으로 실증한다. 셋째, **런타임 introspection**으로 하드코딩 이름표 없이 임의의 pip 라이브러리·로컬 모듈을 블록화하고, 그 위에 초/중/고 점진 공개 교육 큐레이션을 표시 층의 VIEW로 얹는다. IR 변환은 CPython 3.12 전체 `ast` 노드에 대해 **기계 검증된 전수성(raw=0)**과 fail-loud 규율을 지킨다. 186개 IR 게이트 테스트, 퍼즈(AST 동일성), 187 케이스 코퍼스, 종단 골든패스로 무손실성과 전수성을 검증했다. BlockPy는 진짜 AST를 IR로 삼는 결정과 recognition⟂lowering 분리를 결합함으로써, 무손실성을 증명 가능하게 유지하면서 임의 라이브러리로 확장하는 최초의 블록↔텍스트 환경을 제시한다.

**주제어(keywords):** 블록 기반 프로그래밍, 양방향 변환, 무손실 왕복, 추상 구문 트리(AST), 정규 중간 표현, 프로그램 introspection, 컴퓨팅 교육, recognition-lowering 분리

# 부록. 핵심 용어 미니 사전 (가나다순)

앞 장에서 나온 낱말을 빠르게 되짚기 위한 짧은 사전이다. 자세한 설명과 비유는 본문의 해당 절을 보라.

- **값 블록 (value block / 리포터)** — 다른 블록의 홈에 끼워져 하나의 "값"을 대신하는 블록. 파이썬의 식(expression)에 해당한다. (2.7)
- **건전성 정리 (soundness)** — "틀린 인식 오라클은 블록을 잘못 칠할 수만 있고 왕복 코드는 바꾸지 못한다"는 명제. recognition ⟂ lowering 분리에서 따라 나온다. (3.6, 4.2)
- **노드 (node)** — 트리를 이루는 점 하나. 대입·호출·반복 등 한 가지 역할을 맡으며, BlockPy에서 블록 하나와 짝을 이룬다. (1장)
- **뮤테이터 (mutator)** — `[+]`/`[-]` 버튼처럼 블록의 구조(인자 수 등)를 늘리고 줄이는 장치. 늘어난 구조는 `extraState`에 저장된다. (2.10)
- **무손실 (lossless)** — 왕복해도 뜻을 하나도 잃지 않는 성질. BlockPy는 AST 동일성으로 이를 정의·검증한다. (1장, 3.2)
- **문법 (grammar)** — 어떤 토큰 배열이 말이 되는 문장인지 정한 규칙. BlockPy는 파이썬의 진짜 문법을 그대로 따른다. (1장)
- **문장 블록 (statement block)** — 위아래로 쌓이며 실행 순서를 이루는 블록. 파이썬의 한 줄 명령(statement)에 해당한다. (2.7)
- **라이브러리 (library)** — 미리 만들어 둔 기능 꾸러미. BlockPy는 introspection으로 임의 라이브러리를 자동 블록화한다. (2.2, 3.7)
- **렉서 (lexer / tokenizer)** — 소스코드 글자를 토큰 조각으로 잘라 주는 도구. BlockPy는 파이썬 `tokenize`를 쓴다. (1장)
- **로우어링 / lowering (낮추기)** — 블록 → IR → 파이썬 방향으로 코드를 내려쓰는 일. 생성 파이썬의 유일한 진실 원본이다. (1장, 3.5)
- **무손실 계약 → 무손실 / AST 동일성 참조.**
- **블록 (block)** — 명령 하나·값 하나를 담은 색색의 조각. 파이썬 AST 노드 하나에 대응한다. (2.3)
- **소스코드 (source code)** — 사람이 직접 쓴 프로그램 원본 글자. BlockPy에서는 파이썬 텍스트와 블록 그림, 두 얼굴을 가진다. (1장)
- **셰도우 블록 (shadow block)** — 값 홈에 미리 흐릿하게 채워진 기본값 블록. 학생이 안 채워도 프로그램이 말이 되게 지켜 준다. (2.8)
- **시각 프로그래밍 (visual programming)** — 글자 대신 블록을 끌어 맞춰 프로그램을 만드는 방식. (2.1)
- **왕복 (round-trip)** — A→B→A로 되돌아오는 한 바퀴 여행. BlockPy에서는 "파이썬→블록→파이썬". (1장)
- **워크스페이스 (workspace)** — 블록을 실제로 조립하는 캔버스. 여기 놓인 블록만 코드가 된다. (2.4)
- **인식 / recognition** — 블록이 무슨 라이브러리·타입인지 알아채 색·라벨을 입히는 표시 전용 판단. 코드 생성에 개입하지 않는다. (2.14, 3.6)
- **인터프리트 (interpret)** — 코드를 한 줄씩 즉석에서 실행하는 것. BlockPy의 [Run]은 Pyodide로 실제 실행한다. (1장)
- **전수성 (totality / raw=0)** — 파이썬의 모든 노드 종류를 하나도 빠짐없이 처리한다는 성질. `NODE_POLICY`+`ir_coverage.spec.js`가 기계 검증한다. (1장, 3.1)
- **제너레이터 (generator)** — 블록을 텍스트 코드로 바꾸는 변환 규칙. 오직 블록 구조에서만 코드가 나온다. (2.12)
- **직렬화 (serialization)** — 블록 배치를 JSON으로 저장·복원하는 일. 스냅샷 복구의 바탕이다. (2.11, 3.4)
- **추상 구문 트리 → AST 참조.**
- **친수성 → 해당 없음.**
- **코드 생성 / unparse** — 트리·IR을 다시 사람이 읽는 글자 코드로 써 내려가는 것. 파서의 반대. BlockPy는 `ast.unparse`를 쓴다. (1장)
- **컴파일 (compile)** — 코드를 미리 통째로 다른 형태로 번역해 두는 것. BlockPy의 파이썬↔블록 변환이 여기 가깝다. (1장)
- **큐레이션 (curation)** — 거대 라이브러리를 초/중/고 수준별 작은 블록셋으로 골라 ★ 탭으로 보여주는 표시 층 뷰. 새 lowering이 아니다. (3.8)
- **토큰 (token)** — 소스코드를 잘게 쪼갠 의미 있는 최소 조각. (1장)
- **툴박스 / 카테고리 (toolbox / category)** — 쓸 수 있는 블록을 종류별로 정리한 메뉴. 라이브러리마다 카테고리가 자동 생성된다. (2.5)
- **파서 (parser)** — 토큰을 보고 문장의 구조를 알아내는 도구. BlockPy는 `ast.parse`를 쓴다. (1장)
- **플라이아웃 (flyout)** — 카테고리를 누르면 옆으로 펼쳐지는 블록 견본 목록 창. (2.6)
- **필드 (field)** — 블록 안에서 직접 값을 입력·선택하는 칸. BlockPy는 함수명은 고정 라벨, 변수는 드롭다운으로 제한한다. (2.9)

**영문·약어**

- **AST (Abstract Syntax Tree, 추상 구문 트리)** — 문장 구조를 겉모습 빼고 뜻만 남겨 그린 나뭇가지 그림. BlockPy는 CPython 3.12 `ast`를 그대로 IR로 삼는다. (1장, 3.1)
- **AST 동일성 (AST equivalence)** — 두 코드를 파싱한 트리가 같은지로 무손실을 판정하는 기준: `ast.dump(parse(원본)) == ast.dump(parse(재생성))`. (1장, 3.2)
- **fail-loud** — 모르거나 잘못됐을 때 조용히 넘기지 않고 즉시 오류로 멈추는 규율. `noHandler`/throw. (1장, 3.4–3.5)
- **IR (Intermediate Representation, 중간표현)** — 파이썬과 블록 사이의 공통 중간 형태. BlockPy에서는 파이썬 AST를 담은 JSON. (1장)
- **`ir_*` 블록** — 파이썬 AST 노드에 1:1 대응하도록 BlockPy가 정의한 블록군(`ir_call`, `ir_if` 등). (2.14)
- **recognition ⟂ lowering** — 블록의 "색칠(인식)"과 "코드 생성(번역)"을 데이터 흐름상 직교로 분리한 BlockPy의 핵심 설계이자 안전장치. (2.14, 3.6, 4.2)
